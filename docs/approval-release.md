## الفحص المسبق

`release-approval.py` أداة جديدة تخص هذه الخطة والصورة. تستورد فقط تعريفات
مساعدة خاملة من أداة الإصدار السابق (Docker API، الحفظ الذري، قفل النشر،
تركيب إعدادات الحاوية وفحص الصحة). لا تستدعي مسار النشر أو التحقق أو
الاسترجاع القديم ولا تغير ثوابته.

```sh
python3 -B scripts/release-approval.py --plan /path/to/private-approval-plan
```

الوضع الافتراضي لا يغير قاعدة الإنتاج ولا الحاويات ولا ملفات الخطة. يتحقق من
الصورة ومصدرها، بصمة الترحيل والنسخة الاحتياطية المجربة، نشاط الحسابين ودوريهما،
عدم تطبيق الترحيل سابقاً، مطابقة الحاويات الثلاث، صلاحية تكوين nginx، وتطابق
ملف هاتف وبيئة الحاوية. أي اختلاف يوقف العملية قبل النشر.

يجب أن ينجح هذا الفحص قبل التطبيق. لا تستخدم `release-operations.py` أو
`deploy.sh` أو خطة الإصدار السابق لنشر هذا التحديث.

## التطبيق بعد اعتماد النتيجة والصورة المحددة

```sh
python3 -B scripts/release-approval.py \
  --plan /path/to/private-approval-plan --apply \
  --approved-image sha256:cc84170de3567a868a6c9605b526744705dc58f469f3055545f2e6e0c5f639a3
```

تأخذ الأداة قفل النشر المشترك وتكتب إيصال محاولة دائم، وتنشئ نسخة قاعدة بيانات
حديثة وتتحقق من فهرسها. تعيد التحقق من الخطة وهاتف بعد النسخ، ثم تطبق الترحيل
الواحد في معاملة ذرية ذات مهلة للأقفال. يُقرأ معرفا الموافقين من الخطة الخاصة؛
لا توجد معرفات حسابات الإنتاج في المصدر.

بعد التحقق من قاعدة البيانات وبيئة التشغيل، توقف الحاوية الرئيسية لفترة
الاستبدال، وتحتفظ بالحاوية والصورة الأصليتين. تستخدم الصورة الجديدة مع متغيرات
التشغيل والمنافذ والشبكات نفسها، بما فيها هاتف. تتحقق من صحة الدخول ورفض API
للطلبات المجهولة محلياً وعبر النطاق العام، ومن بقاء واجهتي الوسيط والحساب.

ملفات `migration.private.json` و`cutover.private.json` توثق التقدم. وجود
`apply-started.private.json` يمنع إعادة التطبيق آلياً، حتى إذا فشلت المحاولة.
إذا فُقد رد قاعدة البيانات بعد بدء المعاملة، تُسجل النتيجة كمجهولة ولا تتوقف
الحاوية الرئيسية تلقائياً. افحص الإيصال وحالة القاعدة قبل تحديد الخطوة التالية؛
لا تحذف العلامة وتعد المحاولة.

## الاسترجاع

فشل تبديل الحاوية يحاول استرجاع التطبيق السابق تلقائياً. قبل حذف حاوية مرشحة،
يتحقق الاسترجاع من صورة التطبيق وعلامة هذه المحاولة، ومن بقاء الحاوية الأصلية
وإعداداتها، ومن مطابقة ملف هاتف. لا يحذف حاوية غير مرتبطة بهذه المحاولة.
إذا انقطعت العملية أو فشل الاسترجاع، يمكن بعد مراجعة الإيصالات تشغيل:

```sh
python3 -B scripts/release-approval.py \
  --plan /path/to/private-approval-plan \
  --rollback /path/to/private-approval-plan/release-TIMESTAMP \
  --approved-image sha256:fc2208da1baee389905f1febd4212a11f69be03f45767ceed3e872272a472506
```

الاسترجاع للتطبيق فقط؛ تبقى البيانات وترحيل المراجعتين. لا تستعد نسخة قديمة
من قاعدة الإنتاج تلقائياً. الواجهة السابقة لا تشرح المرحلتين، رغم أن القاعدة
تبقى تمنع تجاوزهما، لذلك راجع واجهة المالية قبل استئناف العمل المالي بعد
الاسترجاع. يرفض الاسترجاع أسرار هاتف القديمة إذا تغير ملف الإعداد الدائم.

## التحقق

اختبارات أداة النشر تغطي النجاح، الاسترجاع الصريح والمتكرر، فشل عمليات Docker
وفقد ردودها، فشل الصحة وتغير بيئة المرشح، الانقطاع، حماية الحاويات غير المرتبطة،
تغير هاتف والنسخة الاحتياطية، الفحص المسبق دون كتابة، فشل النسخ/SQL/التحقق،
ومنع إعادة محاولة خطة بدأ تطبيقها. اختبار PostgreSQL 17 يثبت التراجع عن جميع
تغييرات DDL عند فشل متأخر داخل المعاملة ثم نجاح المعاملة الصحيحة وحفظ البيانات.
اختبارات Docker تستخدم محاكاة؛ لم تنفذ هذه الأداة تبديل حاويات الإنتاج بعد.

بعد النشر، يؤكد المستخدم ظهور المساعد لمحمد فقط، ومراجعة محمد ثم اعتماد سالم
في الاستخدام الفعلي. لا تنشئ تحصيلاً أو مصروفاً وهمياً في قاعدة الإنتاج للاختبار.
لا تشارك سجلات التنفيذ الخاصة أو runtime/plan JSON أو ملفات النسخ الاحتياطي.
